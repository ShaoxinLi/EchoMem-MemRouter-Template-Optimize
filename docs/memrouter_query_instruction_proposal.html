MemRouter 查询指令生成方案设计

从"路由到哪个后端"升级为"生成后端查询指令"

一、问题陈述

当前 MemRouter 只输出 backend_id（如 openviking_memory_backend），后端内部的具体检索参数（target_uri、context_type、level、search_mode）完全没有明确。

这导致即使 MemRouter 已识别出意图（如 matched_template_id = "openviking.personal_fact_lookup.en.v2"），OpenViking 仍需要重新走 IntentAnalyzer（消耗 ~3K-15K VLM tokens），才能生成具体的检索参数。

目标：让 MemRouter 在零 LLM token 成本的前提下，为每个后端生成可直接执行的查询指令

二、核心洞察：模板语义蕴含查询规格

当前模板 YAML 已经包含大量语义信息，只是没有被充分利用来生成查询指令：

模板字段 蕴含的查询信息
intent_family.name "personal_fact_lookup" → 个人事实查询 → context_type=memory
target.primary_backend_id 目标后端决定了查询参数格式（OpenViking vs Graph vs Temporal）
query_prototypes 原型 query 风格暗示了搜索模式（find vs search vs graph traversal）

关键发现：模板不仅是"路由锚点"，更是"查询规格锚点"。我们只需要在模板中显式声明查询规格，就能让 MemRouter 直接输出后端可执行的查询指令。

三、方案设计

推荐 方案一：模板内嵌查询规格（Template Query Spec）

在现有 YAML 模板中增加 query_spec 字段，声明命中该模板时应生成的查询指令参数。

3.1.2 新增核心数据结构

# echomem/query_spec.py
from pydantic import BaseModel
from typing import Any, Dict, List, Optional

class TypedQueryTemplate(BaseModel):
    """类似于 OpenViking 的 TypedQuery，用于直接生成检索请求。"""
    query: str
    context_type: str            # "memory" | "resource" | "skill"
    intent: str
    priority: int = 1
    target_directories: Optional[List[str]] = None

class OpenVikingQuerySpec(BaseModel):
    """OpenViking 后端特定查询规格。"""
    context_type: str
    target_uri: str
    level: Optional[List[int]] = None
    filter: Optional[Dict[str, Any]] = None
    skip_intent_analysis: bool = False
    typed_query_template: Optional[TypedQueryTemplate] = None

class GraphQuerySpec(BaseModel):
    """Graph 后端特定查询规格。"""
    graph_query_type: str        # "entity_relation" | "causal_multihop" | "system_dependency"
    hop_depth: int = 1
    root_entity_hint: Optional[str] = None
    traversal_direction: str = "both"   # "out" | "in" | "both"

class TemporalQuerySpec(BaseModel):
    """Temporal 后端特定查询规格。"""
    temporal_query_type: str     # "timeline_fact" | "duration_comparison" | "sequence_reasoning"
    time_granularity: str = "day"
    time_range_hint: Optional[str] = None

class TemplateQuerySpec(BaseModel):
    """模板级查询规格，命中模板时直接产出。"""
    search_mode: str = "find"    # "find" | "search" | "read" | "graph_traversal" | "temporal_query"
    query_rewrite: Optional[str] = None   # 支持变量插值

    # 后端特定规格
    openviking: Optional[OpenVikingQuerySpec] = None
    graph: Optional[GraphQuerySpec] = None
    temporal: Optional[TemporalQuerySpec] = None

class MemBackendRouteResult(BaseModel):
    schema_version: "mem-router.backend-route-result.v2"
    raw_user_query: str
    normalized_user_query: str
    route_method: str
    routes: List[RouteEntry]

    # ========== 新增 ==========
    query_instructions: List[BackendQueryInstruction] = []
    # ==========================

    fallback: FallbackInfo = Field(default_factory=FallbackInfo)
    debug: DebugInfo = Field(default_factory=DebugInfo)

class BackendQueryInstruction(BaseModel):
    """标准化的后端查询指令，后端可直接执行。"""
    backend_id: str
    query: str                        # 重写后的查询文本（支持变量插值）
    search_mode: str                  # "find" | "search" | "graph_traversal" | "temporal_query"
    target_uri: Optional[str] = None
    context_type: Optional[str] = None
    level: Optional[List[int]] = None
    filter: Optional[Dict[str, Any]] = None
    priority: int = 1
    # 后端特定参数透传
    extra_params: Dict[str, Any] = Field(default_factory=dict)
    # 是否跳过后端内部 intent analysis
    skip_intent_analysis: bool = False

备选 方案二：Adapter 内建映射表（Adapter Query Mapping）

不在模板中增加字段，而是在每个 Adapter 内部维护一个 intent_family → 查询参数 的映射表。

# echomem/adapters/openviking.py
class OpenVikingAdapter(MemoryBackendAdapter):
    # intent_family → OpenViking 查询参数映射
    _INTENT_QUERY_MAP: Dict[str, Dict[str, Any]] = {
        "personal_fact_lookup": {
            "context_type": "memory",
            "target_uri": "viking://memories",
            "level": [2],
            "search_mode": "find",
            "skip_intent_analysis": True,
        },
        "preference_profile": {
            "context_type": "memory",
            "target_uri": "viking://memories/preferences",
            "level": [0, 1, 2],
            "search_mode": "find",
            "skip_intent_analysis": True,
        },
        "aggregation_summary": {
            "context_type": "memory",
            "target_uri": "viking://memories",
            "level": [0, 1],
            "search_mode": "search",   # 需要 session 上下文做聚合
            "skip_intent_analysis": False,
        },
        "previous_chat_recall": {
            "context_type": "memory",
            "target_uri": "viking://memories/sessions",
            "level": [2],
            "search_mode": "search",   # 需要 session 上下文
            "skip_intent_analysis": False,
        },
    }

    def generate_query_instruction(self, route_result: MemBackendRouteResult) -> BackendQueryInstruction:
        route = self._resolve_route(route_result)
        intent_family = self._extract_intent_family(route.matched_template_id)

        spec = self._INTENT_QUERY_MAP.get(intent_family)
        if not spec:
            # 未知 intent：回退到 search 模式，不跳过 intent analysis
            return BackendQueryInstruction(
                backend_id=self.BACKEND_ID,
                query=route_result.raw_user_query,
                search_mode="search",
                skip_intent_analysis=False,
            )

        return BackendQueryInstruction(
            backend_id=self.BACKEND_ID,
            query=route_result.raw_user_query,
            **spec,
        )

优点：模板 YAML 无需修改，向后兼容。

缺点：映射表与模板解耦，新增模板时需要同步修改 adapter 代码；无法支持模板级别的个性化参数。

推荐混合 方案三：模板主导 + Adapter 补全（Template-First Hybrid）

结合方案一和方案二的优点：

  • 模板 YAML 提供 query_spec 基础规格（高置信时的默认参数）
  • Adapter 提供 运行时补全逻辑（根据 query_hints 动态调整参数）
  • 如果模板未提供 query_spec，回退到 adapter 映射表
# 决策流程
def generate_query_instruction(route_result, adapter):
    template = resolve_template(route_result.matched_template_id)

    # Step 1: 从模板获取基础规格
    if template and template.query_spec:
        base_spec = template.query_spec
    else:
        base_spec = adapter.get_default_spec(template.intent_family.name)

    # Step 2: Adapter 运行时补全（根据 query_hints）
    final_spec = adapter.enrich_spec(
        base_spec=base_spec,
        hints=route_result.routes[0].query_hints,
        raw_query=route_result.raw_user_query,
    )

    return BackendQueryInstruction(**final_spec)

这是最灵活的方案，既保持了模板的声明式配置能力，又保留了 adapter 的运行时智能。

四、与 OpenViking 的深度集成：跳过 IntentAnalyzer

4.1 当前 OpenViking 的检索入口

# OpenViking 当前流程
client.search(query, session=session)
  → VikingFS.search(query, session_info=...)
    → if session_summary or current_messages:
        → IntentAnalyzer.analyze()  ← VLM 调用 (~3K-15K tokens)
        → 生成 QueryPlan (TypedQueries)
      else:
        → 直接构造 TypedQuery
    → HierarchicalRetriever.retrieve(TypedQuery)

4.2 集成后的新流程

# MemRouter + OpenViking 集成流程
client.route(query)
  → MemRouter Pipeline
    → TemplateMatcher.match()  ← 本地 embedding，零 token
    → RouteDecision.decide()
    → 生成 BackendQueryInstruction:
        {
          "backend_id": "openviking_memory_backend",
          "query": "你还记得我喜欢什么颜色吗",
          "search_mode": "find",
          "context_type": "memory",
          "target_uri": "viking://memories",
          "level": [2],
          "skip_intent_analysis": true,
          "typed_query": {
            "query": "你还记得我喜欢什么颜色吗",
            "context_type": "memory",
            "intent": "personal_fact_lookup",
            "priority": 1
          }
        }

# OpenViking 侧新增：接收预构造的 TypedQuery
client.execute_instruction(instruction)
  → if instruction.skip_intent_analysis and instruction.typed_query:
      → 跳过 IntentAnalyzer
      → 直接用 instruction.typed_query 构造 HierarchicalRetriever
    → HierarchicalRetriever.retrieve(instruction.typed_query)
      → 无需 VLM，直接进入向量检索

4.3 Token 成本对比

场景 当前流程 集成后流程 节省
个人事实查询（高置信模板命中） MemRouter 本地匹配 + OpenViking VLM intent analysis (~3K-15K tokens) MemRouter 本地匹配 + 直接向量检索（零 VLM tokens） ~3K-15K tokens
聚合摘要查询（需要 session 上下文） VLM intent analysis skip_intent_analysis=false，仍走 VLM 0（设计如此）
LLM fallback 场景 MemRouter LLM fallback + OpenViking VLM MemRouter LLM fallback 直接生成完整指令 节省 OpenViking 侧 VLM

关键设计：skip_intent_analysis 是一个策略开关，不是强制跳过。模板设计者可以根据意图类型决定是否需要 session 上下文：

  • personal_fact_lookup → skip_intent_analysis=true（个人事实不依赖 session 上下文）
  • previous_chat_recall → skip_intent_analysis=false（需要 session 历史）
  • aggregation_summary → skip_intent_analysis=false（需要 session 上下文做聚合）

六、向后兼容性

维度 兼容性策略
模板 YAML query_spec 为可选字段；旧模板无该字段时，adapter 回退到映射表
Result Schema query_instructions 为可选字段；旧 consumer 忽略即可

Adapter 接口 MemoryBackendAdapter 新增 generate_query_instruction() 抽象方法，旧 adapter 可渐进实现

  • 扩展 MemBackendRouteResult 支持 query_instructions

  • 实现 OpenVikingAdapter.generate_query_instruction()
  • 建立 intent_family → OpenViking 参数 映射表（作为 fallback）
  • 为 4 个 OpenViking 模板编写 query_spec
  • 单元测试：验证指令生成正确性

Phase 3：OpenViking SDK 集成（3-5 天）

  • OpenViking SDK 新增 execute_instruction(instruction: BackendQueryInstruction) API
  • 实现 skip_intent_analysis 分支：直接构造 TypedQuery 进入 HierarchicalRetriever
  • 端到端测试：MemRouter → OpenViking 零 VLM token 路径

Phase 4：评测与调优（2-3 天）

  • 扩展 eval_memrouter.py：评测 query instruction 准确率
  • 对比实验：有/无 query instruction 的 OpenViking 检索效果
  • Token 成本核算：实际节省了多少 VLM tokens

八、收益总结

收益项 说明
Token 成本降低 高置信个人记忆类 query 可完全跳过 OpenViking IntentAnalyzer，节省 ~3K-15K VLM tokens/次
延迟降低 跳过 VLM 调用，直接进入向量检索，延迟从数百毫秒降至数十毫秒
端到端可控 MemRouter 生成完整查询指令，后端不再需要自行推断，链路可追踪
向后兼容 所有新增字段为可选，不影响现有代码路径
可扩展性 新增记忆后端时，只需注册 backend + 编写模板 query_spec + 实现 adapter

九、风险与缓解

风险 缓解措施
模板 query_spec 与后端实际能力不匹配 skip_intent_analysis 为策略开关，默认 false；只有高置信场景才启用
变量插值（如 {entities}）为空导致 query 质量下降 插值失败时回退到 raw_user_query，不报错
意图族映射表维护成本 模板 YAML 自包含 query_spec，不依赖外部映射表；adapter 映射表仅作 fallback
